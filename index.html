Chapter 1

RecastEngine

The engine is the reusable part of SciRecast. It reads legacy source, writes the modern version, compiles the untouched original as the reference, and refuses to call the result correct unless a gate says so. It knows nothing about any particular model: domain knowledge attaches through plugins, and the engine passing its tests with every domain package uninstalled is a standing check.

New here? Getting started takes you from an empty machine to a verified translation of your own module in about twenty minutes. This chapter is the map.

1.1One spine

discover → analyze → transform → verify → record

Every workload walks the same five steps. A frontend discovers the units of a source tree and analyzes each into facts; a transform turns the facts into a candidate; an oracle builds the reference; verifiers compare candidate and reference and return a verdict; a store records the verdict as evidence. A recipe is a list of those stages with a plugin named for each slot, and which stages are gates.

1.2Four recipes

RecipeWhat it does, and how far it reaches
translateFortran to NumPy, Numba or CUDA, gated bit-exact against the compiled Fortran. Runs end to end. target: tree bundles the sibling modules a unit uses.
portRetarget a kernel to JAX (or Numba, CUDA), gated on a ULP bound against the NumPy translation, or on captured production dumps with oracle: dump-replay. Runs end to end.
auditSecret scan and SBOM, CVE and VEX, gating the way a DevSecOps pipeline does. Plans clean on the shipped scanners.
refactor-todoRestructure architecture without touching numerics, gated on a full model run. Declares four slots nothing fills yet; the name carries its incompleteness.

recast recipes lists them; recast plan <recipe> shows the stages a run would walk and marks a slot nothing fills as [MISS], before anything compiles. 

$ recast plan translate --config '{"target": "numba"}'
 1. [ok ] executor     local
 2. [ok ] frontend     fortran
 3. [ok ] transform    translate.numba
 4. [ok ] verifier     static.rwset                 gate
 5. [ok ] oracle       f2py-golden
 6. [ok ] verifier     differential.bitexact        gate
 7. [ok ] verifier     symbolic.notary              optional
 8. [ok ] store        fs-evidence

1.3Ten kinds of plugin

Every capability arrives through an entry point, including the engine's own: there is no privileged built-in path. This is what the engine registers with no domain extension installed.

KindAnswersRegistered
frontendwhat the units of a tree are, and the facts about eachfortran
transformthe candidatetranslate.numpy translate.numba translate.cuda translate.tree port.jax port.tree-jax
oraclethe reference to compare againstf2py-golden f2py-golden-flat numpy-anchor dump-replay

scannerfindings over a repositorysecret composition

executorwhere a job runslocal
storewhere verdicts and findings gofs-evidence fs-findings

recipethe stages of a workloadtranslate port audit refactor-todo

A domain extension adds to this list by declaring the same entry-point groups, with no change to the engine: the CESM extension supplies a cesm frontend, a translate.cam transform and a translate-cam recipe that way, and the CLM-ml extension of §2.2 a clm-ml frontend and its own oracle. recast plugins prints what is registered, by kind. To write one, implement the interface in src/recast/plugins/ and run the conformance suite against it; writing-a-plugin.md walks through it.

1.4What a gate concludes

A verdict carries a confidence that says what kind of claim it makes, and the countable metrics behind it. On the engine's own example, a thirty-line column integration:

VerifierConfidenceMetrics
static.rwsetsampledblocks_checked=4, blocks_matched=4
differential.bitexactbit_exactpoints=85, bit_exact=85, max_ulp=0
symbolic.notarysymbolicrewrites=0

Every run writes one manifest per verdict under output/, and --summary writes the current state to one file that is byte-identical across two correct runs, meant to be committed beside the code it vouches for. The engine's CI regenerates the example's summary on a clean machine and fails on any difference. Reading the evidence says what each field means and what a passing run does not claim; docs/ has the rest.

Chapter 2

CESM Case

The first model the engine is used on: the Community Earth System Model. Two atmosphere pipelines, one land-model reproduction, and a shared validation layer. Every component is its own repository.

2.1Two pipelines

Pipeline 1Pipeline 2
ModelCAM5CAM6
ApproachRewrite to Python and decouple the physics into modules; Codon-compiledRewrite to Python/JAX and Numba, GPU-accelerated kernels
BarBit-for-bit with the native Fortran, selected at run time per entry pointScheme by scheme against native CESM output
RepositoriesPyCAM5, freeCAMJaxCAM6, NumbaCAM6 (private)

PyCAM5 replaces the Fortran with Codon-compiled Python inside the CAM component. freeCAM comes from the other end: Python owns the control path, clock and coupling, and the original Fortran keeps supplying the numerics through generated bind(C) adapters.

2.2The canopy model, held to the Fortran for a month

The land side is where the engine's evidence reaches furthest. The multilayer canopy of the Community Land Model (CLM-ml v2, 76 Fortran modules) was taken to NumPy and JAX under the engine and a small domain extension, reproducing arXiv:2606.07681:

  • all 15 canopy physics modules bit-exact against the Fortran on the model's own recorded state;
  • the whole time step bit-exact on 902,544 points, and the closed-loop month bit-for-bit in NumPy;
  • the JAX month inside the paper's 1% band by one to four orders of magnitude, with gradients through the full step;
  • two defects found in the upstream model by the gates, reported as issues rather than patched.
Honest note

Soil hydrology and the tower forcing stay recorded rather than closed, and the throughput figure is a single-point CPU number. The full account, with every intermediate number, is case-clm-ml.md.

2.3Validation and security

A separate layer by design: a gate the gated thing can influence is not a gate.

CC-Testthe CI gate for both Correctness and Cyber testing: the same secret scan, SBOM and CVE check, source audit and sanitizer builds run locally before a push and in the cloud on every pull request
Sec-Track (restricted)the record of N-day and responsibly disclosed vulnerabilities across the modernized software, its dependencies and the runtime; access is granted per person, so it is listed here by name and never as a number

Chapter 3

Contributing

Where to send what, and how to extend the engine.

3.1Where to send what

What you haveWhere it goes
A translation that is wrong, or a rule that should existRecastEngine issues, with the console output of the run
A bug or an idea in a componentthat component's own repository: PyCAM5, freeCAM, CC-Test
A security vulnerabilitynever a public issue: a private GitHub security advisory, or the address below

3.2Extending the engine

Implement one of the ten interfaces in src/recast/plugins/ and register an entry point; writing-a-plugin.md walks through it. Knowledge of your model or your cluster belongs in a plugin, not in the engine: the engine passing its tests with every domain package uninstalled is a standing check.

3.3Contact

Security vulnerabilities, collaboration, and licensing: Yueqi Chen, University of Colorado Boulder, yueqi.chen@colorado.edu. For a vulnerability, please do not open a public issue.
